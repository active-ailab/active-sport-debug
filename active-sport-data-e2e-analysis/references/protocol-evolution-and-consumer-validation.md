# 协议演进与消费者验收

## 一、为什么要分阶段

一次运动数据协议修改至少包含七个相互独立的门：

| Gate | 验收对象 | 通过证据 |
|---|---|---|
| G1 生产 | 算法/Service 产生正确业务值 | 同一样本原始日志、值和语义 |
| G2 跨核/跨设备 | 参数布局与宏一致 | 两端结构、长度、magic/version 和日志 |
| G3 序列化 | record tag 写入正确字节 | 原始 TLV/二进制独立解码，或受限说明 |
| G4 APP 解析 | 新字段被正确还原 | parser 输出与固件字段逐值一致 |
| G5 业务消费 | 算法/统计实际使用新字段 | 最终输入日志或源码赋值闭环 |
| G6 展示/上传 | UI/云端使用正确口径 | 页面/上传参数与真实边界对照 |
| G7 兼容 | 新旧组合行为可预期 | 四象限回归结果 |

G4 通过不能替代 G5/G6。某个二次算法已使用新字段，而详情页仍使用旧时间线，就是典型的消费者分叉。

每个 Gate 同时检查两种正确性：

- **传输正确性**：数值和字节是否原样到达。
- **语义正确性**：消费端是否把该数值当成正确的业务量使用。

原始字节完全一致但字段被错误命名或用作错误时间边界，仍属于业务失败。

## 二、协议字段设计检查

- 优先传递业务真实值，不让消费者从异步节点时间反推边界。
- 字段名必须匹配语义。记录提交时间不能命名成站点开始时间。
- 明确单位、时钟域、原点、有效范围和无效值。
- 相对数组必须同时携带明确基准。例如 REP 偏移必须绑定站点起点。
- 尾插字段要明确结构长度、版本判定和旧解析器行为。
- 多个 tag 复用同一 `relative_time` 只说明节点复用，不能证明它们共享正确业务边界。
- 若宏改变跨核结构布局或解析分支，必须检查两端配置、结构大小、对齐和 magic 是否满足同一通信契约；核分工按 [大小核配置与跨核链路](core-configuration-and-routing.md) 确认。

## 三、四象限兼容矩阵

| 固件 | APP | 预期 |
|---|---|---|
| 旧 | 旧 | 历史行为不变 |
| 旧 | 新 | 新 APP 能识别字段缺失并走明确回退，不越界读取 |
| 新 | 旧 | 旧 APP 能忽略尾部扩展，或明确不支持的版本边界 |
| 新 | 新 | 使用新字段，完成业务消费和展示验收 |

再叠加业务开关、运动模式和大小核宏组合。若产品只承诺部分组合，报告中明确支持边界，不要求不存在的兼容性。

## 四、同一记录跨版本回放

### 适用场景

- APP parser 或业务消费修复。
- UI 时间线修复。
- 同一协议记录在不同组件版本中的行为对比。

### 做法

1. 固定同一份原始运动记录、trackId 和校验值。
2. 记录旧/新 APP 及 parser、业务算法组件版本。
3. 分别采集 parser 输出、业务算法输入、算法输出和详情页窗口。
4. 逐字段对比，不重新做一场运动作为唯一 A/B 样本。
5. 对变化项指出首次分歧层，对不变项确认没有回归。

### 边界

- 可隔离 APP 变量，但不能证明固件新字段生成过程正确。
- 服务端记录若会变，需固定下载内容或保存 hash。
- 同一 APP 多次触发算法时，要确认每次输入是否相同；次数相同不代表内容相同。

## 五、证据血缘与跨问题复用

为每份关键材料记录：

| 字段 | 内容 |
|---|---|
| source_issue | 来源 Jira/反馈编号 |
| artifact | 附件名或服务端记录标识 |
| sha256 | 原始文件校验值 |
| track_id/session | 运动样本身份 |
| producer_version | 固件、算法 tag、协议版本 |
| consumer_version | APP、parser、业务算法组件版本 |
| covered_gates | 该材料直接证明哪些 Gate |

复用规则：

1. 同一 trackId 且原始记录内容/hash 一致，可把已验证的生产/协议证据与新 APP 消费证据拼成同一血缘链。
2. trackId 不同但代码版本相同，只能复用实现机制，不能复用具体时间值和“当前样本通过”结论。
3. 旧报告没有原始附件或版本不完整时，应降级证据强度并说明。
4. 跨 Jira 引用必须写明引用了哪一段结论，不能只写“沿用之前分析”。

## 六、证据等级

| 等级 | 证据 | 可以证明 |
|---|---|---|
| A | 原始 TLV/二进制独立解码 + 两端值一致 | 序列化布局和值正确 |
| B | 固件写入日志 + APP parser 输出逐值一致 | 端到端透传高度可信，但未独立证明原始字节/CRC |
| C | APP parser 输出 + 业务输入一致 | APP 内部消费映射正确 |
| D | UI 截图/单端摘要日志 | 用户现象或局部行为，不足以证明上游 |

报告必须写实际达到的等级。例如未独立重解码原始 TLV 时，应写“日志交叉验证通过，原始字节解码未覆盖”，不能写“协议字节完全验证”。

## 七、相对时间和数组的闭环验算

对基准加偏移类字段，至少检查：

```text
absolute_start[i] = base_start + offset_start[i]
absolute_end[i]   = base_start + offset_end[i]
base_start <= absolute_start[i] <= absolute_end[i] <= base_end
```

同时检查：

- 空数组站点验证字段布局不依赖动作数量。
- 有动作站点验证首末动作和总数量。
- 跨包/chunk 场景验证顺序连续、不重复、不丢失。
- 暂停恢复站点确认偏移采用 wall time 还是 active time。
- `base_end` 若未进入消费者，不得用 `base_start + lap_time` 宣称精确等价。

## 八、修复完成定义

协议类问题只有在以下内容分别给出状态后才能关闭：

1. 新字段生产正确。
2. 序列化和解析正确。
3. 目标业务消费者已切换。
4. 其他消费者已检查，不存在“一个修好、一个仍旧”的遗漏。
5. 新旧组合符合兼容承诺。
6. 正向样本、空值样本和至少一个异常时序样本已覆盖。

如果此次需求只修复某个消费者，也可以验收通过，但必须把其他消费者标为“不在本次范围”或“独立缺口”，不能写成整条 APP 链路完成。
