# 端到端运动数据分析

## 目标

把同一笔运动在各端的事实投影到一条可计算、可复核的时间轴，回答：

1. 数据由谁产生，业务语义是什么。
2. 各层何时接收、转换、缓存、落盘、上传和展示。
3. 偏差从哪一层开始，后续只是传播还是再次放大。
4. 修复应落在哪一层，兼容和回归范围是什么。

不要只搜索同名字段后直接下结论。字段名相同不代表语义相同；时间戳相近也不代表可以互换。

## 核心原则

- **先定版本，再谈行为**：记录项目、分支、commit/patchset、算法 tag、固件版本、APP 版本、功能宏和业务开关。不同版本的证据不可无说明混用。
- **先定语义，再算差值**：区分采样时刻、算法业务边界、回调时刻、LAP 构建时刻、记录节点写入时刻、上传时刻和展示时刻。
- **以生产端业务边界为基准**：存在明确 `start_ts/end_ts`、`station_end_ts` 等字段时，优先用它们；不得默认用记录节点 `relative_time` 反推业务边界。
- **累计量与分段量分开**：总距离、总消耗等累计量通常不回退；LAP/站点距离、配速、心率、功率、体温和次数要按边界结算。
- **原始证据优先**：协议原值和原始日志高于 UI 截图；截图用于确认用户可见现象，不单独证明数据源。
- **结论分级**：明确标注“已证实”“高可信推断”“待验证”，不得把缺失证据写成通过。
- **分析与发布分离**：读取 Jira/Gerrit/飞书可按任务执行；评论、上传附件、修改文档或提交代码前必须有用户明确授权。

## 输入分流

先列出已有材料和缺口，不要立即钻进单个日志：

| 输入 | 主要用途 |
|---|---|
| 需求/HLD/算法接口文档 | 定义目标行为、业务边界、模式和异常策略 |
| Gerrit/本地源码 | 确认真实生产消费链路、宏分支和版本差异 |
| 固件日志 | 还原算法输出、Engine 回调、Service 状态机、落盘字段 |
| 运动记录/协议 dump | 核对节点 tag、字段值、相对时间和序列化布局 |
| APP 日志 | 下载、解密并按同一 trackId 核对解析、模型转换、算法输入、详情页展示和上传 |
| 截图/录屏 | 锚定用户现象和可见时间窗口 |
| Jira/群聊结论 | 获取复现条件和团队已确认约束，不替代代码与日志证据 |

串口实时日志遵循工作区 `AGENTS.md`，优先使用 Agent Log CLI，不能直接抢占 COM 口。Jira/Gerrit 使用 `zepp` CLI；飞书文档操作按 `lark-doc` skill。需要真机测试时再使用相应设备测试 skill。

## 标准工作流

### 1. 冻结分析范围

建立版本矩阵，至少包含：

- 运动类型、模式、主从设备角色、外设连接状态。
- 自动/手动分段、暂停恢复、校准状态等关键开关。
- 固件与 APP 版本，源码分支和相关 Gerrit patchset。
- 样本唯一标识：trackId、session 起点、设备、测试日期。
- APP parser、业务算法/SDK 等独立组件版本，不能只记录 APP 外层版本号。

从日志标签确认版本所属层：设备固件、设备算法、APP、APP算法/组件分别登记。分析老版本时，当前源码只可解释机制；需由对应历史代码或现场日志确认实际行为。再核对校准、模式、有效输入等条件，确定争议数据实际进入的算法分支，不能仅凭运动名称套用专项路径。

如果日志来自不同次运动，按样本分别建时间轴，禁止拼成一条链路。

建立证据血缘表：记录 Jira、附件、trackId、文件 hash、产生端版本和消费端版本。只有同一原始记录或可证明内容一致时，才允许跨 Jira 沿用逐值结论；相似场景只能复用机制说明。

### 1.1 提取并解析 APP 日志

APP 日志不是普通文本附件时，先按 [APP 日志提取与解析](references/app-log-extraction-and-parsing.md) 执行：

1. 在独立工作目录下载 Jira 附件或质量平台反馈包，保留原始文件。
2. 展开压缩包；对 Logan 文件运行 `zepp app delog`，同时生成 `*-decode.txt` 和 `*-decode.jsonl`。
3. 用 `trackId`、运动开始时间和运动类型锁定唯一 session，再提取协议解析、持久化、业务算法输入、算法输出和详情页五类证据。
4. JSONL 优先用于精确过滤，TXT 用于查看多行上下文和未结构化大字段；两者来自同一源文件时不要重复计为两份独立证据。
5. 将命中项整理为 `文件:行号 + 日志时间 + tag/thread + 原始字段 + 所属消费链路`，再进入后续时间轴分析。

若 APP 日志没有覆盖目标 session，或只能找到 UI 展示而找不到 parser/模型输入，必须标记链路缺口，不能用其他运动样本补成当前样本的直接证据。

### 2. 建立数据契约表

涉及固件 Engine 的问题，先按 [大小核配置与跨核链路](references/core-configuration-and-routing.md) 确认编译核、执行核和代理方向，再定位字段生产者。同名函数、共享头文件和公共目录不能单独证明执行位置。

涉及数据项支持范围或跨项目遗漏时，按 [运动数据项配置](references/sport-data-item-configuration.md) 追踪 `sports.xlsx`、生成器、项目属性头文件与运行时映射，分别确认配置支持、有效出值、页面展示和记录保存。

对每个争议字段记录：

```text
字段 -> 生产者 -> 单位/时钟域 -> 累计或分段 -> 更新频率
     -> 转换/缓存 -> 协议字段 -> APP模型 -> 最终展示/算法输入
```

重点判断：

- 当前值是瞬时值、窗口均值、本站累计、整场累计还是上一段结果。
- `rep_count` 是本包增量还是本站累计。
- `rep_start_ms` 相对哪个起点。
- LAP `relative_time` 是业务边界还是节点提交时刻。
- 暂停时间使用 wall time、运动净时长还是算法时钟。
- 已恢复暂停是否计入total、从net扣除；最后未恢复暂停是否从两者排除；APP派生终点究竟使用哪个时长字段。

详细规则见 [时间语义与不变量](references/time-semantics-and-invariants.md)。

### 3. 双向追踪调用链

同时执行两条追踪，直到在协议字段处闭环：

1. **正向**：算法/传感器输出 → Engine → Service listener/状态机 → cache → record save → tag/字段。
2. **反向**：APP 页面/算法输入 → ViewModel/数据库 → 协议 parser → 对应记录 tag/字段。

每一跳保留源码文件、函数、条件宏和关键赋值式。不要止步于包装 API；继续确认它使用的是传入快照、当前全局值还是延迟缓存。

### 3.1 建立消费者分叉清单

协议 parser 输出后，不要再把“APP”视为单一消费者。枚举所有下游并逐项验收：

| 消费者 | 典型用途 | 必须单独确认 |
|---|---|---|
| 本地模型/数据库 | 保存解析结果 | 字段是否持久化、类型和单位是否变化 |
| 二次算法 | 训练分析、负荷评估等 | 实际输入字段、数组下标和缺省值 |
| 详情页 | LAP/站点展示 | 是否仍使用旧时间线或派生字段 |
| 上传链路 | 云端记录/统计 | 序列化字段和服务端最终落库 |
| 导出/分享 | 对外数据 | 是否复用详情模型或独立计算 |

“parser 已识别新字段”只表示解析层通过；只有消费者实际输入日志或源码赋值闭环后，才能写该消费者通过。

### 3.2 协议演进分阶段验收

涉及新增字段、尾插结构或跨核消息时，按 [协议演进与消费者验收](references/protocol-evolution-and-consumer-validation.md) 分阶段确认：生产、跨核、序列化、解析、业务消费、展示/上传、兼容。任何阶段未覆盖都要单列，不能用后一阶段的成功倒推前一阶段正确。

### 4. 构造统一时间轴

选定统一基准，优先使用 UTC epoch ms；只有相对时间时，明确其原点。每个事件至少记录：

| 字段 | 含义 |
|---|---|
| sample | 样本/trackId |
| entity | session、lap、station、rep 等实体 |
| layer | Algorithm、Engine、Service、Record、APP、UI |
| core/route | 大核/小核/外部设备，以及 local/remote 调用方向 |
| event | start、change、final、write、parse、display 等 |
| timestamp | 原始时间值 |
| clock/origin | UTC、运动净时长、相对站点起点等 |
| evidence | 日志行、协议字段、代码位置或截图 |
| confidence | 已证实/推断/待验证 |

先做毫秒数值对照，再转为人类可读时间。统一公式直接写入报告，例如：

```text
动作绝对时间 = station_start_ts + rep_offset_ms
站点真实时长 = station_end_ts - station_start_ts
展示起点偏差 = app_start_ts - station_start_ts
展示终点偏差 = app_end_ts - station_end_ts
```

整场结束、暂停或实时/离线结果不一致时，读取 [运动结束与聚合窗口分析](references/session-end-and-aggregation-windows.md)。用“固件实时算法、固件运动记录、APP运动记录、APP算法”四列比较启动、暂停、恢复、确认保存和结束；分别标注现场事件时刻、记录派生时间和算法窗口边界。

### 5. 按数据类型验证不变量

不要用“页面看起来合理”代替计算。至少验证：

- 时间窗口是否单调、无重叠/遗漏，REP 是否落在站点 `[S,E]`。
- 分段距离之和是否与整场距离口径一致，配速是否使用同一段的时间和距离。
- 分段卡路里/功率/体温/心率是否按相同边界结算。
- 总量是否保持单调，边界修正是否只改变归属而不重复累计或扣减总量。
- 暂停、恢复、延迟尾包、重复通知、断连和空数据是否改变状态机预期。

按具体指标核查时读取 [跨层核对清单](references/cross-layer-checklist.md)。

### 6. 找到首个分歧点

根因定位遵循“最早错误原则”：

1. 上游原值正确、序列化错误：协议/记录层问题。
2. 协议正确、APP parser 错误：解析兼容问题。
3. parser 正确、业务模型使用错字段：APP 消费语义问题。
4. 二次算法输入正确、详情页错误：两条消费链路需分别定性，不能整体判失败。
5. 所有层值正确但 UI 延迟：展示刷新或异步调度问题。

区分历史共性问题与新功能增量问题。若总偏差由多项叠加，拆成公式，不把全部归因给最近改动。

### 7. 交叉验证与反证

至少使用两类独立证据支持关键结论，例如：

- 固件日志原值 + APP parser 后日志。
- 协议 dump + APP 算法输入。
- 源码赋值关系 + 同一样本数值等式。

主动检查反例：旧版本、关闭开关、手动流程、无外设、暂停恢复、最后一站退出。无法覆盖时写入残余风险。

若问题集中在 APP 消费修复，优先使用**同一运动记录跨版本回放**：让旧 APP 和新 APP 消费完全相同的记录，以排除传感器、算法和运动过程差异。回放只能证明消费端差异，不能替代对固件生产端的独立验证。

输入窗口或字段不同与最终分数差异属于两个验证层次。若需量化某因素对分数的贡献，应固定算法版本、初始状态及其他输入，仅替换该因素回放；在此之前只确认已复现的输入差异，不按分钟数直接推算分值。

### 8. 输出与回传

正式报告使用 [报告模板](references/report-template.md)，先给结论，再给逐站/逐段证据。报告必须包含：

- 分析范围与版本矩阵。
- 用户现象和量化偏差。
- 端到端链路图。
- 数据契约和统一时间轴。
- 首个分歧点、根因、影响范围。
- 修复建议、兼容策略和验收用例。
- 已验证、未覆盖与证据索引。

写 Jira 评论时压缩为结论、证据、影响、建议四部分；长报告作为附件。创建飞书文档时使用原生表格和流程图，完成后回读关键字段与链接。

## 停止条件

满足以下条件才可给出“根因已确认”：

- 同一样本已贯通生产字段、记录字段和至少一个消费端。
- 数值公式能够复现用户看到的偏差。
- 已定位第一个出现错误语义或错误数值的层。
- 已解释为何旧流程可能正常、新流程为何暴露，或证明与新功能无关。

否则输出当前最强结论和最小补证清单，不用猜测补齐链路。
